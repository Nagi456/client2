# 更新の運用

## 現在の状態

- 本体の配布履歴で、26.51.1の2つ前からは **26.45.1 / 26.50.4 / 26.51.1 / 26.52.3**。
- DLLをビルド済みなのは26.51.1（LeviLamina Client 26.51.6）。他の3版は対応SDK/アダプターが未準備で、一覧では「対応待ち」。番号を書き換えただけでは対応できない。
- 自動更新のコードと公開用ファイルを用意した段階。GitHubへの公開はまだ行っていない。
- 本体のダウンロード・旧版導入・ワールド分離は未実装。導入済みの対応GDK本体が必要。
- WindowsのGUI/通信/Minecraft実機テストは未実施。Linuxのテスト・クロスビルドは実機テストの代わりにならない。

## Zoom・FPS・防具を追加した版

現在の同梱DLLは0.3.0、更新リビジョンは3です。Hive Party用に独立したParty.v1チャンネルを追加しました（Hive実機未検証）。矢・照準座標のABI 2は維持し、Features.v1チャンネルを追加しました。以前のHUDはこの新しい表示・操作に対応していないため、これらの機能を使う初回は新しいZIP全体を展開してください。以後、同じHUD/通信方式のDLL修正は更新機能で配布できます。

## 利用者の操作

ランチャー起動時に対応一覧を取得する。版を選んで「適用して起動」を押すと、必要なDLLとローダーの設定を取得する。同じリビジョンを保存済みなら再利用する。ネットワーク障害や未公開の場合は保存済み一覧を維持する。新しいDLLの取得失敗時に古いDLLへ黙って戻さず、エラーを表示して再試行できるようにする。

DLLファイルは取得中の一時フォルダーで検査し、全ファイルの検査完了後にキャッシュへ移動する。本体の版・ローダー版・DLLの依存関係を照合する。起動中のゲームのDLLは交換せず、ゲームを終了した次の起動で適用する。

保存先は `%LOCALAPPDATA%/MyClient/`：

- `catalog.json`：最後に取得・検査できた配布一覧
- `packages/<ゲーム版>/<revision>/`：検査済みのDLL・依存設定・ライセンス
- `game/<ゲーム版>/`：本体の専用コピーとその版のMOD
- `launcher.json`：選択した版と版ごとの元ファイルの場所

本体コピーを版ごとに分けても、**ワールド保存先は現在共有**。新しい本体で開いたワールドを旧版で開くと破損する場合がある。旧版でのプレイを提供する前にワールド分離を実装・実機検証すること。既存のワールドを自動移行しない。

## 配布元

起動時に読む固定URL：

`https://github.com/Nagi456/MyClient/releases/download/client-catalog/catalog.json`

DLL等は同じリポジトリの各リリースに置く。HTTPSの証明書検証と、一覧に記録したSHA256/サイズを使う。GitHubの当該リポジトリを信頼元とし、任意の第三者URLやHTTPは受け付けない。ローダー自体は従来どおりLiteLDevの固定版URLから取得する。署名付きオフライン配布には未対応。

公開後はGitHubを読めるPCから認証なしで取得するため、配布ファイルが公開アクセス可能であることが必要。個人用アクセストークンをランチャーへ埋め込まない。

## 初回公開（管理者が行う）

1. Windows実機で26.51.1とランチャーの準備・DLL接続を確認する。
2. `tools/package_update.py` で更新用ファイルを生成する。
3. GitHubのリリースタグ `myclient-26.51.1-r3` に、生成した同名フォルダーの**個々のファイル**をアップロードする。アセット名を変更しない。
4. リリースタグ `client-catalog` のアセット `catalog.json` を**最後に**公開する。先にDLL等を公開・取得確認し、未完成の一覧を利用者に渡さない。
5. 配布ZIP `MyClient-26.51-hive-x64.zip` を公開する。以前の更新非対応ランチャーの利用者には、この版への初回更新が必要。

```sh
python3 tools/package_update.py --sdk-root /path/to/client-sdk --output /tmp/myclient-release-assets --catalog launcher/catalog.json --revision 3 --sequence 3
```

このコマンドは公開用ファイルを作るだけで、GitHubには書き込まない。

## DLLの修正・新しいゲームへの対応

1. 対象本体に合うSDK/ローダーでアダプターを修正・ビルドし、実機検証する。
2. 同じゲーム版の修正では `revision` を増やす。一覧を変更するたび `sequence` も増やす。
3. 直前に公開した一覧を `--catalog` に渡し、既存の対応版を保持する。
4. 新リビジョンの個別アセットを公開し、すべて取得できることを確認する。
5. `client-catalog` の `catalog.json` を差し替える。

例（現在のリビジョン3を修正してリビジョン4を配布）：

```sh
python3 tools/package_update.py --sdk-root /path/to/client-sdk \
  --catalog /path/to/published/catalog.json --revision 4 --sequence 4 \
  --output /path/to/output/updates
```

別のゲーム版では、検証済みの `runtime.lock.json` と `mods/MyClientData/` を含むフォルダーを準備し、`--package-dir /path/to/package --game-version 26.52.3` を追加する。対応DLLがない状態でこの操作をしない。配布ツールの検査はゲームとの互換性を保証しない。

同じリビジョンのファイルは上書きしない。問題のある版は一覧で `available: false` にしてsequenceを増やす。修正版にはさらに新しいrevisionを割り当てる。保存済みの古いゲーム版は維持する。

## ランチャーの更新が必要になる場合

DLLと依存ローダーの更新だけなら再インストール不要。ただし現在の対応範囲は Windows x64 GDK、通信ABI 2、ランチャーAPI 1、既存の6依存ローダー構成。HUD通信形式・導入方式・ランチャー本体を変更する場合は新ランチャーが必要で、一覧に理由を表示する。EXE自身を差し替える自己更新機能は含めていない。

## 故障時

更新取得をやり直すには「更新を確認」を押す。破損キャッシュを検出した場合はMinecraftとランチャーを閉じ、該当する `packages/<版>/<revision>/` だけを退避して再取得する。ゲーム本体やワールドを削除しない。DLLの以前の設定とバックアップはゲーム側の `MyClient-backups/` に残る。
